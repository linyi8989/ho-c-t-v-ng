2. P1 — Có lỗi phân quyền thật trong role resolution

Đây là phát hiện quan trọng nhất.

Trong:

src/server/accessPolicy.ts

logic hiện tại về cơ bản là:

const claimRole = decodedToken.role;

if (VALID_ROLES.has(claimRole)) {
  return claimRole;
}

const storedRole = storedProfile.role;

return VALID_ROLES.has(storedRole)
  ? storedRole
  : "student";

Tức là:

Firebase custom claim được ưu tiên hơn role lưu ở backend.

Nhưng khi admin thay đổi role trong server.ts, code lại làm:

await userRef.update({ role });

try {
  await adminAuth.setCustomUserClaims(targetUserId, { role });
} catch (...) {
  // warning
}

Nếu bước cập nhật custom claim lỗi, database vẫn báo role mới nhưng quyền thực tế có thể tiếp tục lấy từ token cũ.

Tôi đã kiểm tra trực tiếp logic:

Firebase claim = super_admin
DB role        = student
=> kết quả: super_admin

và ngược lại:

Firebase claim = student
DB role        = super_admin
=> kết quả: student
Hậu quả

Ví dụ admin hạ:

super_admin → student

Database đã là student, nhưng token cũ còn:

role: super_admin

thì user vẫn có thể được backend nhìn nhận là super_admin.

Điều này đặc biệt nguy hiểm trong trường hợp:

tài khoản giáo viên/admin bị mất quyền;
cần khóa ngay tài khoản;
cần hạ quyền ngay;
Firebase custom claim update gặp lỗi;
token chưa refresh.

CODEMAP lại mô tả backend-stored role là authoritative, nên code hiện tại không khớp design intent.

Tôi đề nghị sửa

Authority nên là:

1. Backend stored role
2. Firebase claim chỉ dùng bootstrap/fallback
3. configured bootstrap admin chỉ dùng khi profile chưa được khởi tạo

Ví dụ:

const storedRole = String(storedProfile?.role || "").trim();

if (VALID_ROLES.has(storedRole as AppRole)) {
  return storedRole as AppRole;
}

const claimRole = String(decodedToken?.role || "").trim();

if (VALID_ROLES.has(claimRole as AppRole)) {
  return claimRole as AppRole;
}

return "student";

Và test hiện tại cũng cần sửa, vì test security của bạn đang vô tình đóng đinh behavior sai này.

Nên thêm regression test:

assert.equal(
  resolveTrustedRole(
    { role: "super_admin" },
    { role: "student" },
    configuredAdmins
  ),
  "student"
);

Nhưng các phần “core/current” cũ vẫn có những mô tả đã lỗi thời, ví dụ:

automatic Firestore fallback
old email-by-phone behavior
old scoring description
hardcoded super-admin
old release artifact/version

Ngoài ra trước đó tôi còn phát hiện duplicate section 16.

Đối với project một người phát triển nhỏ thì đây chỉ là inconvenience.

Nhưng khi CODEMAP được dùng làm:

AI development specification
deployment handbook
audit source

thì nó trở thành operational risk.

Tôi vẫn đề nghị cấu trúc:

PART A — CURRENT STATE
chỉ mô tả code hiện tại

PART B — RELEASE PROCEDURES

PART C — CHANGELOG
§19...
§80...
§85...

Không để current architecture và lịch sử vá lỗi trộn với nhau.

Release gate tôi yêu cầu trước khi cho GO
Sửa resolveTrustedRole() để backend stored role là authority và thêm regression test cho downgrade super_admin → student.
Khôi phục root package-lock.json, xóa node_modules, xác nhận npm ci chạy sạch trên Node 22.16.0 / ABI 127.
Sửa tsconfig.json, sau đó chạy thật npm run lint; không cập nhật CODEMAP thành PASS nếu command chưa PASS.
Chạy nguyên npm run test:phase1, đặc biệt native better-sqlite3 storage/startup/history tests.
Dùng bản copy production SQLite đã anonymize: backup → quick_check → migration §83 → chạy migration lần hai → kiểm tra row count → duplicate token → backfill → readiness marker.
Chặn traffic trong toàn bộ migration/backfill window, không chỉ “quiesce rồi start Passenger”.
Chạy browser smoke §84–§85: MP3/YupVox/fallback/mute/race; Fill Enter-focus; Matching colors.
Chuyển Home leaderboard sang bounded summary hoặc ít nhất kiểm tra lại payload/TTFB với database production-size.
Xử lý/triage lại 3 high npm audit findings mà CODEMAP trước đó ghi nhận.
Chỉ sau các bước trên tôi mới chuyển verdict từ NO-GO → GO.

Điểm đáng ghi nhận là SQLite production path, fail-closed storage, archive lifecycle, guest point-read, §83 hot path và §84–§85 đều được triển khai thực sự chứ không chỉ ghi trong CODEMAP. Vấn đề lớn hiện tại không còn nằm ở “ý tưởng kiến trúc”, mà nằm ở authorization authority, reproducible build/test và release discipline.

Nếu sửa đúng 3 blocker đầu tiên, chất lượng codebase có thể nhảy khá rõ từ khoảng 7.2 lên vùng 8/10 mà chưa cần refactor lớn.
