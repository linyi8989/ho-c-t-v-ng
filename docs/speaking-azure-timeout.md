# Speaking Azure connection and assessment deadlines

The WAV upload, immutable file/hash and queued job were present for the failed recordings. Recent sentence jobs failed at the application's overall provider deadline; previous sentence jobs had completed in about two seconds. The old process was no longer running when connection diagnostics began, so its exact network state cannot be reconstructed from the generic stored error.

An unpaid diagnostic reproduced a stalled SDK WebSocket handshake in a network-restricted process: no connection callback after 15 seconds. Running the same SDK/configuration with outbound network access connected in 945ms; Azure token authentication returned HTTP 200. These checks started no recognition and sent no audio. This demonstrates that process network restrictions can produce the reported timeout; it does not prove that every historical failure had that cause.

`azureSession.ts` opens the SDK connection before starting recognition, with a separate 15-second deadline. The assessment deadline starts after connection and retains the previous duration + 60 seconds, capped at six minutes. Late/repeated callbacks cannot start a second assessment or overwrite a settled result. Continuous recordings still collect all phrases through end-of-stream/session-stop, without grading partial results after a timeout. Word cancellation uses SDK `CancellationDetails` instead of becoming a misleading no-speech result.

Known cancellation codes produce safe connection, authentication, permission/quota, service-busy, request, service-timeout or service-failure messages. SDK endpoint/error text is never returned or logged. Cleanup cannot leave the job promise unresolved or replace its original outcome. The service retains its existing owner checks, WAV, failed History status, null score, explicit retry limit, quotas and provider selection. No schema or queue behavior changes.

Localhost was restarted using Node 22.16.0, `dev:local:native`, native SQLite WAL, History enabled and seeds disabled. A native verified backup was taken first. A read-only guard confirmed zero outstanding Speaking jobs before restart: no old failed recording was retried automatically. No `.env` changes.

Verification: 64 Speaking tests pass, typecheck/canonical build pass, compiled-server Speaking smoke passes. New session tests cover stalled handshakes, late callbacks, full continuous phrases, a connected session that never ends, cancellation categories, safe errors, word success/no-match/cancellation, malformed JSON and cleanup failure. Earlier recorder browser tests cover synthetic microphone capture, stop/send/cancel/flush race, playback/retained upload, device errors and desktop/mobile layouts. Actual localhost browser checks are GET-only with zero writes or runtime exceptions.

The requested live assessment of one stored student WAV was blocked by automatic approval review because sending that private recording to Azure can incur a service charge and needs explicit payload/destination authorization. It was not executed or replaced with another paid request. Token/WebSocket checks and mock/synthetic offline tests are complete; real grading still needs approval or a student-initiated test.
